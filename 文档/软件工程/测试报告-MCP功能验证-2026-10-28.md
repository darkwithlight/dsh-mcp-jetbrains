## 三、关键发现

### 1. `build_project` 会"假成功"——这是最重要的一条

对一个**有明确类型错误**的文件：

```java
public class Main {
    public int broken() {
        return "not an int";   // 编译错误
    }
}
```

`build_project` 返回：

```json
{"isSuccess":true,"problems":[]}
```

**没有任何构建系统时，IDE 报"成功且零问题"，而不是"没构建"。** 这与本文档第十二节记的「空 problems ≠ 干净」是同一类陷阱的更强版本：不是"没分析"，而是**明确声称成功**。

结论：`build_project` 的 `isSuccess` 不能单独作为"代码没问题"的依据；在无构建系统的项目上它恒为 true。

### 2. `lint_files` / `get_file_problems` 会给出"未分析"而非"干净"

对同一文件：

```json
{"filePath":"src\\Main.java","notAnalyzedReason":"File is outside project content roots or in an excluded directory","problems":[]}
```

空项目（`.idea` 里只有 `misc.xml` 与 `workspace.xml`，**没有模块 `.iml`**）的文件不在内容根内，因此**不分析**。此时 `problems: []` 与"检查通过"长得一模一样——必须读 `notAnalyzedReason` 才能区分。

### 3. 路由模式会吃掉参数里的单引号

用绝对路径调用时：

```text
read_file --file_path D:/shing_of_kai/SourceCode/ShaoZhu'sDSHPlugins/.../package.json
→ Error: File D:/shing_of_kai/SourceCode/ShaoZhusDSHPlugins/.../package.json doesn't exist
```

注意 `ShaoZhu's` 变成了 `ShaoZhus`——**单引号被路由模式的 `--name value` 解析吞掉**。路径含单引号时，应使用**相对于项目根的路径**，不要把绝对路径塞进 `command` 字符串。

### 4. 「读写走 IDE」的路由确实按最长前缀工作

`idea` 与 `idea_tmp` 同端口、不同 `projectPath`，两类文件分别落到正确连接（用例 4、5）。`diagnostics` 的 `connection` 字段是事后核查路由的唯一依据，值得保留。

### 5. 拒绝是彻底的：既不写盘也不误伤其它连接

项目外写入被拒绝时，错误里同时列出**两条候选连接**，并说明"有 2 条已启用连接，无法唯一确定"——而不是随便挑一条。磁盘确认未被创建（用例 6）。

## 四、结论与建议

**可用性**：读、写、编辑、搜索、目录树、终端、拼错诊断、路由鉴权均在真实环境跑通；「读写走 IDE」的强制语义（含拒绝路径）符合设计。

**风险提示（建议写进使用文档）**：

1. **不要用 `build_project` 判断代码健康**——无构建系统时它恒成功。要走 `lint_files` / `get_file_problems`，并且**必须检查 `notAnalyzedReason`**。
2. **新建的空项目默认不可分析**，需要先让 IDE 建立模块与内容根（打开一次、或让 IDE 导入构建文件）。
3. **含单引号的路径**在路由模式下要用相对路径传参。
4. 经 IDE 写入的文件是 **CRLF**（跟随项目设置），与 DSH 原生写入的 LF 不同；有行尾约定的仓库需注意。

**后续可做**：把"未分析/假成功"的判定做进插件层——例如在调用 `build_project` 后自动补一次 `get_file_problems`，或在 `notAnalyzedReason` 非空时显式标注"未检查"。
